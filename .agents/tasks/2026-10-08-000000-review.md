# Payment stats and transaction matching fixes

The changes address three bugs that prevented payment statistics from displaying and alert fundraising amounts from updating: missing admin API endpoints, incorrect transactionRef extraction from digiKUNTZ responses, and inconsistent minimum payment validation. Two backend files and two Angular modal components were modified.

**Watch for:** The admin endpoints lack pagination - the 500-record limit is a blunt guard that will hide data beyond 500 transactions (confirmed). Old transactions stored with `REF-` fallback refs will never match webhooks and require manual recovery via the new `mark-success` endpoint (confirmed). The 15 XAF minimum is a temporary test value that needs to revert to 100 XAF before production (confirmed by user).

**Verdict**: APPROVED

## High-level view

The admin panel's `loadPaymentStats()` called three GET endpoints that simply didn't exist in the backend. Every call returned 404, caught silently by `.catch(() => [])`, so all stats stayed at zero. The new `GET /admin/payments/transactions` and `GET /admin/payments/payout-requests` endpoints fill that gap with Admin-only guards.

The transactionRef extraction from digiKUNTZ was producing the `REF-${Date.now()}` fallback even though `data.data.transactionRef` was present in the response. The new code explicitly chains `data['data']?.['transactionRef']` before falling back to top-level keys, and logs a warning if the sentinel is triggered.

Old transactions created with `REF-` refs are permanently mismatched - incoming webhooks carry `IN331#...` and `findOne({ transactionRef })` finds nothing, so `raisedAmount` is never incremented. The new `POST /admin/payments/mark-success/:transactionId` provides a manual recovery path: an admin identifies the stuck transactions (PENDING status, REF- ref), verifies payment externally, and calls the endpoint to transition the transaction to SUCCESS and apply the `$inc`.

The 15 XAF minimum is a test value replacing the 100 XAF threshold in four places (two backend guards, two frontend `submit()` guards). A minor UI inconsistency remains: `platform-support-modal` shows the recap div when `effectiveAmount >= 1` but validation rejects amounts under 15.

1. **Unpaginated admin transactions endpoint** - `GET /admin/payments/transactions` hard-codes `limit(500)` with no offset or cursor. Add pagination parameters or switch to cursor-based paging before production.

5. **Recap threshold inconsistency** - `platform-support-modal.component.ts` template shows recap when `effectiveAmount >= 1` but validation requires `>= 15`. Change the `*ngIf` condition to `effectiveAmount >= 15`.

## Admin stat endpoints - 500-record ceiling

All three new endpoints are on `AdminPaymentController` (prefix `/admin/payments`) with `JwtAuthGuard + RolesGuard + @Roles('Admin')`. The `transactions` endpoint accepts optional `type` and `status` query params, which is what the frontend sends (`type=DONATION_ALERT&status=SUCCESS` and `type=PLATFORM_SUPPORT&status=SUCCESS`). The `payout-requests` endpoint is a fixed filter for `type=PAYOUT_REQUEST`.

The `limit(500)` on `getTransactions` is the concern: there is no offset, cursor, or total count returned. Once the DB has more than 500 transactions matching the filter, the admin panel silently shows an incomplete subset. For current MVP volume this is fine, but it should be addressed before production.

## TransactionRef extraction - old data cannot be healed

The digiKUNTZ response nests the ref at `data.data.transactionRef`. The old code's `inner['transactionRef']` should have reached it (since `inner = data['data'] ?? data`), but message 10 logs show the fallback `REF-1791447065707` was being stored even when the response contained the correct value. The regression is not entirely explained by the diff - the old code looked structurally correct. Regardless, the new explicit chain through `data['data']?.['transactionRef']` with an extraction log on every call makes regressions immediately visible:

```
[digiKUNTZ] extracted transactionRef=IN331#261008081040 from data.data={...}
```

If this log ever shows `transactionRef=undefined`, the warning fires immediately before the fallback is used.

Transactions already in the DB with `REF-` refs are permanently broken for webhook matching. The `mark-success` endpoint requires an admin to verify payment externally (digiKUNTZ dashboard) before calling it - there is no idempotency key or double-approval guard, so calling it twice on a SUCCESS transaction returns early (`'Déjà marquée SUCCESS.'`), which is safe.

## Minimum threshold - four places, no feature flag

The `amount < 15` guard in `initiateDonation` and `initiateSupport` now matches the frontend's `isValid` getter. Previously `submit()` in both modals checked `< 1`, meaning a user could submit a 1 XAF payment that would pass the frontend but be rejected by the backend. That mismatch is fixed.

The `platform-support-modal` template has `*ngIf="effectiveAmount >= 1"` for the confirmation recap. With the threshold now at 15, entering 10 XAF shows the recap ("Don de **10 XAF**") while the submit button is disabled. The condition should be `>= 15`.

There is no feature flag, env var, or constant centralising the minimum amount. Reverting to 100 XAF before production requires four manual changes.

## Not tested

No test files are in the diff. The admin endpoints, transactionRef extraction, and minimum validation are exercised only through manual testing.
